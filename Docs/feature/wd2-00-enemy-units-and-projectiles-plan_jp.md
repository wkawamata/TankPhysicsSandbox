# WD2-00 敵ユニットと敵弾の実装計画

更新日: 2026-10-04
状態: 実装前の計画。以下の型名・ファイル名は設計案。
仕様: [WD2-00 敵ユニットと敵弾の開発仕様](wd2-00-enemy-units-and-projectiles-spec_jp.md)

## 方針と到達点

移動しない破壊可能な固定砲台を起点に、敵通常弾・敵特殊弾、自機の被弾・Lost・GameOver・Continueまでを段階的に実装する。
敵通常弾は自機の通常弾と迫撃砲で迎撃でき、敵特殊弾は迎撃で破壊されない。

各段階はビルド可能な小さな変更として完了させる。既存の車両挙動・通常弾・破壊可能オブジェクトを維持する。
本計画の設計案や提案値は、ゲーム仕様の確定事項と区別する。未確定事項に依存する本実装は、該当段階の開始前に仕様を決める。

## 現状と再利用箇所

| 対象 | 現状 | 計画 |
| --- | --- | --- |
| AssaultWeapon / CombatTarget | Enemy・Destructible・EnemyProjectileの種別、HP・active、被弾結果がある | 耐久力・破壊判定を再利用する。ワールド上の敵・敵弾との接続は追加する |
| TrackedVehicleTest | 通常弾の移動・線分衝突、破壊可能な静的箱、破壊時のBody除去がある | 敵ユニット・敵弾のワールドアダプターと統合テストの入口にする |
| TankController | 自機物理・通常弾・特殊移動・迫撃砲照準を管理する | 被弾状態の連携と、自機だけの復帰操作を追加する |
| 迫撃砲 | 照準角度・射程・攻撃半径・canFireと範囲表示がある | 発射イベント、着弾、ダメージ・迎撃判定が必要。照準表示だけで迎撃済みと扱わない |
| TrackedVehicleMode / ScenePresenter / Panel | ワールド更新、通常弾の表示、破壊可能箱の表示、デバッグUIがある | 敵・敵弾・HP・残機・Continueの表示と操作を追加する |
| MapManifest | playerSpawn、instances、clearAreasがある | 敵専用の配置・設定データは段階的に追加する |

## 責務とデータ境界

- `PlayerCombatState`（案）: HP・残機・Alive/Lost/GameOverと被弾イベントを管理する、レンダラー非依存の小さな状態機械。
- `EnemyUnit` / `FixedTurretController`（案）: 耐久力、攻撃タイマー、照準、発射要求を管理する。自機のTankControllerを敵砲台用に流用しない。
- `EnemyProjectile`（案）: 種別、迎撃可否、耐久力、接触ダメージ、位置・速度、形状・寸法、寿命、発射元IDを持つ。
- `CombatSettings` / JSON（案）: 自機HP・開始残機、砲台設定、敵弾タイプ定義を扱う。配置データとタイプ定義を分ける。
- ワールドアダプター: Jolt Body・衝突・生成・除去を担当し、戦闘イベントを状態機械へ渡す。
- TankController: 自機の物理状態と被弾状態を連携し、自機の復帰時に必要な物理・入力状態を更新する。
- Rendering / UI: 公開スナップショットを読み、表示と操作要求を担当する。HP減少や迎撃成功を描画側で決めない。

最初から汎用エンティティ基盤や大規模な継承階層は作らない。既存のCombatTargetを利用しつつ、敵ユニットと敵弾のライフサイクルを別に管理する。
既存コードから共通処理を抽出する必要が生じた場合は、挙動を変えないリファクタリングを独立した変更にする。

## 実装段階

### P0: 未確定事項の整理と設定の境界

- 下記の未確定事項を、必要な段階の開始前に確定する。
- HP100・敵弾ダメージ100・開始残機3を初期値とした設定型とJSONを追加する。
- 既存JSONに項目がない場合は既定値を使用する。敵未配置の既存マップは従来どおり動作する。
- 負値、非有限値、不正な形状・寸法、未知タイプへの方針を定め、エラーで設定が部分更新されないようにする。
- 変更候補: 新規CombatSettings/CombatSettingsJson、Config、CMakeのCoreソース・テスト登録。
- 検証: JSON往復、既定値、不正値、既存設定読み込み。

### P1: 自機のHP・残機状態機械

- HP減少、HP0で1回だけLost、残機減少、残機0でGameOver、Continueを実装する。
- 復帰イベントでHP100、ContinueでHP100・残機3に戻す。
- Lost/GameOver中の追加被弾を新たなLostにしない。同じ固定ステップの複数命中で残機を複数消費しない。
- Lost時の位置をイベントで保存し、復帰先として保持する。
- 変更候補: 新規PlayerCombatState、TankTypes/TankControllerの公開状態との連携。
- 検証: 100ダメージでLost、3回のLostでGameOver、重複命中、非致死ダメージ、Continue、開始時の初期化。

### P2: 固定砲台の配置・耐久力・破壊

- まずテストワールドで固定砲台を明示的に追加できるAPIを設ける。
- 既存の破壊可能箱の被弾・HP判定を再利用する。箱と砲台のIDが衝突しない管理にする。
- 静的な当たり判定を作成し、自機通常弾が命中した対象だけを損傷させる。
- 破壊された砲台は発射不能にし、Bodyを除去する。通常の破壊可能箱は維持する。
- 変更候補: EnemyUnit、TrackedVehicleTest、AssaultWeapon連携。
- 検証: 無効な配置、耐久力の減少、壁による遮蔽、破壊後の弾通過、破壊後の発射停止、初期化時の解放。

### P3: 敵通常弾の発射・移動・自機への命中

- 確定した照準・発射周期に従い、固定砲台から敵通常弾を生成する。
- 発射数・同時存在数に上限を設け、上限到達時の扱いを決める。
- Joltの衝突問い合わせを使って弾の移動区間を検査する。自機判定を除外する既存の自機通常弾用問い合わせをそのまま流用しない。
- 高速弾が自機や地形をすり抜けないよう、形状のサイズを考慮したsweep/shape castを検討する。
- 命中結果をP1に渡し、1つの命中を一度だけ処理する。発射元への接触も仕様に従って扱う。
- 変更候補: EnemyProjectile、FixedTurretController、PhysicsWorld/TankControllerの衝突アダプター、TrackedVehicleTest。
- 検証: 発射間隔、照準、移動距離、遮蔽、高速命中、自機100ダメージ、弾の除去・寿命・上限、破壊済み砲台。

### P4: 自機通常弾による迎撃

- 自機通常弾と敵通常弾の交差を検査し、敵通常弾の耐久力・破壊状態に反映する。
- 両方が動くため、フレーム終端の位置だけでは判定しない。移動区間の相対運動を扱う。
- 地形・敵ユニット・敵弾への命中候補から最初の有効な接触を選ぶ。
- 同一ステップの迎撃と自機命中について、接触時刻を基準に順序を決め、同時刻の優先順位も仕様化する。
- 変更候補: 弾同士の衝突判定モジュール、AdvanceAssaultProjectilesとの接続。
- 検証: 正面交差、斜め交差、すれ違い、壁の向こうの敵弾、高速交差、迎撃済み弾が自機を損傷しないこと。

### P5: 迫撃砲の実攻撃・迎撃

- 既存の照準・canFireから、一度だけ発生する発射イベントを追加する。
- 発射入力、飛翔・着弾時刻、爆風領域、ダメージを確定して実装する。
- 爆風領域と敵通常弾の当たり判定の重なりから迎撃を判定する。
- 敵特殊弾には破壊を適用しない。砲台への迫撃砲ダメージは仕様確定後に接続する。
- 変更候補: MortarAttack（案）、TankController/TankInput、TrackedVehicleTest、迫撃砲表示。
- 検証: canFire前は発射不可、発射の重複防止、範囲内外・境界、複数敵弾、特殊弾の生存、着弾時刻。

### P6: 敵特殊弾と複数形状

- 迎撃可否をタイプ定義で扱い、特殊弾の破壊不可を通常弾・迫撃砲の両経路で保証する。
- 最初に対応する形状と寸法を確定して実装する。任意形状すべてへの対応を初期範囲に含めない。
- 大きな弾も中心点だけで判定せず、形状・サイズに対応する自機接触を扱う。
- 表示形状と物理判定は同じタイプ定義を参照し、DirectX型を物理データへ入れない。
- 検証: 特殊弾の迎撃不能、自機への100ダメージ、形状・サイズごとの接触、無効サイズ、タイプ混在。

### P7: Lost復帰・GameOver・Continueのワールド連携

- Lost時の自機位置を保存し、残機がある場合はその位置で復帰する。
- 自機だけを復帰させる操作を追加する。ワールド全体を再生成する既存Resetを無条件に使わない。
- 復帰時の姿勢・速度・車両内部状態・特殊移動・射撃入力・カメラ追従を整合させる。
- マップ開始位置を別に保持し、Continueでそこへ戻す。Manifestマップと従来MapSpawnの両方を扱う。
- GameOver中の自機操作・敵更新・弾更新の扱いと、Lost/Continueでの敵・敵弾の保持/消去を確定して適用する。
- 変更候補: TankControllerの復帰API、TrackedVehicleTest、TrackedVehicleMode、CameraController連携。
- 検証: Lostは被弾位置、Continueは開始位置、HP/残機、3回目で復帰しない、複数被弾、押しっぱなし入力、敵・敵弾の規定どおりの状態。

### P8: 表示・マップ配置・統合検証

- 砲台、通常弾、特殊弾を識別できる最小表示を追加する。
- HP・残機・Lost/GameOverを表示し、Continue操作を追加する。
- マップに砲台の位置・タイプ参照を保存できるデータを追加する。既存Manifestの読み込み互換性を維持する。
- 初期は固定の検証配置から開始し、マップ保存・読み込みまで実装する。マップエディターの配置UIは追加範囲を決めてから実装する。
- Renderer側だけに表示実装を置く。RtPbrSurveyサブモジュールの変更は前提にしない。
- 検証: 配置の保存・再読込、破壊後の非表示、弾の生成・消去、HP/残機表示、Continue、モード終了・再入場時の解放。

## 先に決める仕様

| 決定事項 | 必要になる段階 |
| --- | --- |
| 砲台HP、発射位置、照準方式、射程、発射周期、遮蔽物越しの発射可否 | P2–P3 |
| 通常弾の形状・サイズ・速度・弾道・耐久力 | P3–P4 |
| 敵弾の寿命・地形接触・自機命中後の消滅、発射元との接触 | P3 |
| 同時存在数と上限時の扱い、同時接触の優先順位 | P3–P4 |
| 迫撃砲の発射入力、弾道・着弾時間・爆風の形状と遮蔽・ダメージ、砲台への攻撃可否 | P5 |
| 特殊弾の最初の形状群、自機弾との衝突時に自機弾が消えるか通過するか | P6 |

無敵時間や残存する敵弾の扱いは、被弾位置での復帰直後に再度Lostとなる可能性に直結するため、復帰連携前に決める。

## ビルド・検証方針

- 各段階でTankPhysicsCoreと対象テストをビルドし、必要なCTestを実行する。
- 既存AssaultWeapon/AssaultProjectile/AssaultDestructible、TankController、車両走行、迫撃砲照準の関連テストを変更範囲に応じて実行する。
- 状態機械はレンダラーなしで検証し、Joltとの統合はTrackedVehicleTestを利用したテストで確認する。
- 最終統合では、固定砲台→敵通常弾→通常弾迎撃、迫撃砲迎撃、敵特殊弾→自機被弾、3回Lost→GameOver→Continueを通して確認する。
- GUI検証は[renderer-development.md](../renderer-development.md)に従い、scripts/run.batとビルドディレクトリの設定を使う。
- CMakeの追加はCoreソース・テスト登録を中心とし、ランタイム配置を変更する場合はrenderer-development.mdの確認事項を適用する。
- プロジェクトのソース・JSON・MarkdownはCRLFを維持する。
- Docs/opencodeおよびユーザーの既存設定・サブモジュール変更を編集対象にしない。

最初はP0の自機設定とP1のHP・残機状態機械を実装し、確定済みのHP100・ダメージ100・残機3・3回LostでGameOver・Continueのリセットをテストで固定する。
その後、砲台と敵通常弾の未確定事項を決めてP2–P4へ進む。迫撃砲・特殊弾・復帰連携・表示を順に追加する。

## 完了条件

- 固定砲台が移動せず、耐久力を持ち、破壊後は発射しない。
- 敵通常弾が自機へダメージを与え、通常弾・迫撃砲で迎撃できる。
- 敵特殊弾が確定した複数の形状・大きさで動作し、迎撃で破壊されず、自機へダメージを与える。
- 初期値で1回の被弾につき1回Lost、合計3回でGameOverとなる。
- Lost復帰は被弾位置、Continueはマップ開始位置・HP100・残機3となる。
- JSON調整と配置保存が動作し、既存マップ・車両挙動・通常弾・破壊可能オブジェクトの関連テストが通る。
- 未確定事項を仕様書へ反映し、実装結果と検証結果を本計画に追記する。

## Type 0追加仕様による計画更新: 2026-10-04

本節をType 0の設定・配置導入の順序として優先する。先行計画の敵設定JSON化とマップ配置は、次の順序へ調整する。
既存の自機CombatSettings JSONは維持する。

| 順序 | 作業 | 検証 |
| --- | --- | --- |
| T0-1 固定値 | 探知範囲・射程範囲・射撃範囲・弾速・発射間隔を持つType 0設定型を定義し、固定値でP3の照準・敵弾発射につなぐ | 探知、各範囲の境界、引きつけて射撃、弾速、発射間隔、破壊後の発射停止 |
| T0-2 JSONロード | 敵タイプ定義をJSONで記述・ロードする。タイプID 0を配置側から参照する | 保存形式、ロード、不正値、範囲の順序、不明なタイプID、失敗時の状態保持 |
| T0-3 敵ユニットエディター | a～eおよび確定した他パラメーターを編集し、敵タイプ定義JSONへSaveする | 編集・保存・再ロードで値が一致、未保存変更の扱い、保存エラー |
| T0-4 マップエディター配置 | 敵タイプを選んで配置し、マップへタイプ参照と配置情報を保存する | 配置・移動・削除、マップ保存・再ロード、既存マップの互換性 |
| T0-5 テストプレイ調整 | 配置した敵と対戦し、a～eを変更・保存して再検証する | 範囲と実射撃の整合、迎撃・被弾・Lost・Continue、設定変更の反映 |

- 敵ユニットのタイプと敵弾の系統を分離する。Type 0は敵通常弾の型番号という意味ではない。
- 探知、射程、射撃開始を同じ閾値にまとめない。
- 範囲の形状を決めてから距離・方向・境界判定を実装する。半径で表す場合は探知 >= 射程 >= 射撃の整合性を検証する。
- 射程の敵弾への適用、遮蔽、範囲から出た後の状態、初弾タイミング、照準方式は実装前に確定する。
- 先行計画P3にT0-1を組み込み、P4～P7の戦闘処理を進める。T0-2～T0-5はその順序を維持し、P8の設定・マップ編集と統合する。
