# Map Editor 仕様

- 作成日: 2026-09-07
- 対象: Tank Physics Sandbox
- 状態: 要件整理。未確定事項と提案は明記する。
- 進捗管理: [実装ステップ・進捗](map-editor-progress-2026-09-07_jp.md)。以後の詳細化・状態更新はこの進捗文書で管理する。

## 1. 目的

glTFで用意した表示用Meshと衝突判定用HitMeshをマップに配置し、主人公戦車の開始地点とクリア判定エリアを編集する。配置情報をMapフォルダ内の `Manifest.json` に保存し、トップ画面からマップを選択してプレイできるようにする。

## 2. 画面遷移

```text
トップ画面
├─ Map Editor
│  └─ 画面左上のOpen → Mapフォルダ選択 → 読み込み／新規作成 → 編集 → 保存
└─ マップ選択 → Play
   └─ 保存されたマップと戦車の開始地点を使ってプレイ
```

- トップ画面のメニューからMap Editorに入れる。
- エディタ画面の左上に `Open` ボタンを設ける。
- `Open` でファイルではなくMapフォルダを選択する。
- フォルダ内に `Manifest.json` があれば読み込む。
- なければ新規の `Manifest.json` を作成する。
- 作成・保存したマップをトップ画面から選択してプレイできる。

## 3. Mapフォルダ

Mapフォルダをマップデータの単位とし、Manifestからモデルを参照する。

```text
ExampleMap/
├─ Manifest.json
└─ Models/
   ├─ Building.glb
   ├─ Ramp.gltf
   ├─ Ramp.bin
   └─ Textures/
```

- 正式なファイル名は `Manifest.json` に統一する（会話中の `Manifext.json` は表記揺れとして扱う）。
- モデルの形式はglTFとする。拡張子 `.gltf` と `.glb` の両対応を提案する。
- モデル参照はMapフォルダからの相対パスとする案。
- `.gltf` が参照するバッファやテクスチャも、マップと一緒に扱える構成にする。
- モデル一覧はMapフォルダ配下のサブフォルダも再帰検索する。リンク・ジャンクション等のreparse pointは検索対象外とする。拡張子の大文字小文字を区別せず、UTF-8相対パス順で表示する。
- Open時にモデル一覧を取得し、Refresh Modelsで再検索できる。検索失敗時は一覧と選択を解除してエラーを表示する。正常な再検索では、同じパスが存在する限り選択を維持する。

## 4. 表示用MeshとHitMesh

### 必須要件

- 表示用Meshと衝突判定用HitMeshを区別して読み込む。
- glTF内の親子関係、または名前付けルールによって役割を認識する。
- 両者を同じ配置単位として、Worldに対する位置・回転で配置する。
- 物理処理はRenderingに依存させない。

### 識別ルール version 1

名前を固定した親ノードによって役割を示し、その子孫のMeshに役割を適用する。

```text
BuildingRoot
├─ Visual
│  ├─ Wall
│  └─ Roof
└─ Hit
   ├─ WallCollision
   └─ RoofCollision
```

- `Visual` 配下: 表示に使用し、衝突形状には使用しない。
- `Hit` 配下: 衝突形状に使用し、通常の描画では非表示とする。
- glTF内の階層変換を反映した上で、Manifestの配置変換を適用する。
- エディタではHitMeshを確認表示できるようにする案。
- 役割を識別できないモデルは理由を表示して追加を止める。

### 詳細規約

- 親ノード名は大文字小文字を区別して `Visual` と `Hit` に完全一致させる。
- 両方の親ノードを必須とし、Meshはどちらか一方の子孫にだけ置く。役割外のMesh、役割ノードの入れ子、循環、複数親はエラーにする。
- 同名・無名のMeshノードも区別できるよう、glTFのノード番号で役割を保持する。
- `Add to Map` はこの検査に成功したモデルだけをManifestへ追加し、`Visual` 側だけを3Dプレビューへ読み込む。`Hit` 側は後続の物理段階まで描画しない。
- glTFノード階層の変換を各Meshへ焼き込み、さらにManifestの配置変換を適用する。

### 座標・変換規約 version 1

- MapのWorld座標は左手系とし、Xを右、Yを上、Zを前とする。距離の単位はメートルとする。
- glTFの右手系データは、ノード階層の変換を適用した後、位置・法線・接線のZを反転して左手系へ変換する。接線の向き成分も反転する。
- glTFノードのTRSはscale、quaternion rotation、translationの順で合成し、子のローカル変換から親へ順に適用する。`matrix` はglTFのcolumn-major配列として読み込む。
- Manifestの `rotationDegrees` は `[X, Y, Z]` の度数法とする。DirectXのroll-pitch-yaw変換へXをpitch、Yをyaw、Zをrollとして渡し、roll（Z）、pitch（X）、yaw（Y）の順に適用してからWorld位置へ平行移動する。
- VisualとHitは同じglTF階層変換とManifest配置変換を使う。ノード階層の変換をManifestへ重複して書かない。

### HitMesh形状規約 version 1

- HitMeshは静的な三角形MeshとしてJoltへ登録する。描画用マテリアル、法線、UV、接線は物理形状に使用しない。
- glTF primitiveはインデックス付きの `TRIANGLES` とし、`POSITION` はfloatの `VEC3`、indexはunsigned byte／unsigned short／unsigned intに対応する。
- bufferViewのbyte offsetとbyte stride、外部BIN、base64埋め込みbuffer、GLBのBIN chunkに対応する。sparse accessorと三角形以外のprimitive modeはversion 1の対象外とし、理由を付けて読み込みを止める。
- Hit配下の複数ノード・複数primitiveは1つの配置用三角形データへまとめる。各ノードの階層変換と右手系から左手系への変換を頂点へ焼き込み、反射変換に合わせて三角形の頂点順を反転する。
- Manifestの位置・回転はJolt形状をWorldへ配置するときに適用する。glTF内の変換と重複して頂点へ適用しない。

## 5. エディタの編集対象

### 5.1 モデル配置

- 選択したMapフォルダ内のglTFデータを一覧表示する。
- 一覧から選択したモデルをロードし、Manifestの配置情報に追加する。
- 配置したモデルのWorld位置XYZと回転XYZをエディタ内で変更する。
- 変更した配置情報をManifestに保存する。
- 同一モデルの複数配置、配置の複製・削除、変更の即時プレビューを提案する。
- 初版は数値入力による編集を提案する。3D画面での選択やドラッグ操作は未確定。

### 5.2 主人公戦車の開始地点

- マップに主人公戦車の最初の出現位置を設定する。
- 開始地点をManifestに保存し、プレイ開始時に反映する。
- 開始地点は1つとし、位置XYZに加えて回転XYZも編集可能にする案。
- エディタでは位置と+Z向きが分かるオレンジ色のマーカーを表示する。

### 5.3 クリア判定エリア

- クリア条件に使うAABBボックスを追加できる。
- エリア情報をManifestに保存する。
- 中心位置XYZとサイズXYZで定義し、World軸に沿わせる。AABB自体の回転は持たせない。
- 複数エリアの追加・編集・削除と名前付けに対応する。
- エディタではシアン色のワイヤーボックスで表示し、物理的に進路を塞ぐ壁にはしない。
- クリア条件version 1は、戦車の車体中心がいずれかのエリア境界内へ入ることとする。境界上も内側として扱い、最初に入ったエリアの名前を保持する。
- クリア後も物理シミュレーションは継続し、走行画面のMap欄へ `MAP CLEAR` とエリア名を表示する。3Dシーンでは達成したAABBをシアンから明るい緑へ変更し、その中心から上へ緑のビーコンを表示する。
- 走行画面では開始地点をオレンジ、クリアAABBをシアンで確認表示し、Map欄からまとめてON/OFFできる。

## 6. Manifestの構造案

以下はデータ構造の提案であり、確定済みのファイル仕様ではない。

```json
{
  "version": 1,
  "playerSpawn": {
    "position": [0.0, 2.0, 0.0],
    "rotationDegrees": [0.0, 0.0, 0.0]
  },
  "instances": [
    {
      "id": "building-001",
      "asset": "Models/Building.glb",
      "position": [10.0, 0.0, 20.0],
      "rotationDegrees": [0.0, 90.0, 0.0]
    }
  ],
  "clearAreas": [
    {
      "id": "goal-001",
      "name": "目的地",
      "center": [0.0, 2.0, 50.0],
      "size": [10.0, 4.0, 10.0]
    }
  ]
}
```

- 位置とサイズの単位はメートル、回転は度数法のXYZを提案する。
- `size` は半径・半サイズではなく、各軸方向の全長とする案。
- Euler角の適用順、軸・座標系、glTFからの座標変換は第4節のversion 1規約に従う。
- Manifestは配置を保存し、Mesh形状そのものはglTF側に保持する。

## 7. 保存とマップ選択

- モデル追加・位置変更・角度変更・開始地点編集・AABB編集をManifestへ反映する。
- 明示的な `Save` 操作で書き込む。通常の編集では自動保存しない。ManifestがないフォルダをOpenした際の新規作成は即時に行う。
- 保存後にトップ画面へ戻り、作成したマップを選択してプレイできる。
- 任意の場所のMapフォルダをトップ画面に表示するため、正常に開いたフォルダを登録・記憶する。
- エディタからトップ画面へ戻るときは、編集していたMapフォルダのManifestをディスクから再読込し、そのフォルダを選択状態にする。これによりビルド出力へ以前コピーされた同名マップより編集元を優先する。
- 登録情報は実行ファイル側の `Config/map_editor_folders.json` にversion 1のUTF-8絶対パス一覧として保存する。再起動時に有効なManifestを再読込し、同名のビルド出力内マップより登録フォルダを優先する。存在しないフォルダや不正なManifestは一覧へ追加せず、トップ画面の読み込み結果へ拒否件数を表示する。
- 未保存状態でのフォルダ切り替え・トップ画面への移動・アプリ終了には、保存して続行／破棄／キャンセルを用意する。Openのキャンセルや読み込み失敗時は現在のデータを維持する。壊れたManifestは上書きせずエラーを表示する。

## 8. 段階的な実装案

1. Manifestのデータ構造・読み書き・検証とテストを追加する。
2. glTFの役割識別と、表示・衝突それぞれへのデータ供給を追加する。
3. トップメニューから入るMap Editorと、Open・モデル一覧・配置編集・保存を追加する。
4. 戦車の開始地点とクリア判定AABBの編集を追加する。
5. トップ画面のマップ選択とプレイへの読み込みを接続する。

各段階でビルド可能な状態を維持し、機能追加と無関係なリファクタリングは分離する。プロジェクトのテキストファイルはCRLFを使用する。

## 9. 検証項目

- Manifestがないフォルダで新規作成できる。
- 既存Manifestを読み込み、保存・再読み込みで配置が保持される。
- glTFの表示用MeshとHitMeshを識別でき、階層変換と配置変換が一致する。
- モデルの位置XYZ・回転XYZが表示と衝突形状に一致して反映される。
- 戦車の開始地点とAABBが保存・復元される。
- トップ画面から保存済みマップを選択してプレイできる。
- 無効なManifest、参照ファイルの欠落、保存失敗時に原因を表示できる。
- 合意したクリア判定ルールに従って境界・侵入・退出を検証する。

## 10. 未確定事項

- HitMeshの対応形状と制約（静的三角形Meshなど）。
- クリア判定の対象点／形状、複数エリアの条件、クリア時の動作。
- トップ画面へのマップ登録・一覧化の方法。
- エディタの数値入力以外の操作範囲。

これらは、要件として決定済みの内容と区別して実装前に確定する。

## 11. 実装状況（2026-09-07）

- 作業ブランチ: `codex/map-editor`（`main` から作成）。
- 初回の変更: 描画・物理ライブラリに依存しない `TankMapCore` と、ManifestのJSONシリアライズ／デシリアライズ。
- この初版では第6節の構造案をversion 1として実装する。回転の適用・クリア判定はまだ行わない。
- モデルのパスはMapフォルダ相対のUTF-8文字列とし、区切りは `/`。拡張子は `.gltf` / `.glb` を大文字小文字を区別せず受け付ける。
- 絶対パス、親フォルダ参照、空のパス要素は受け付けない。ファイルの存在・リンク解決・glTFの外部参照の検証は後続の読み込み層で扱う。
- IDはモデル配置とクリア判定エリアを通して一意とする。
- XYZには有限のfloat値を使用し、AABBサイズは各軸で正の値を要求する。
- 無効な入力による既存データの上書きを防止し、エラーを返す。
- フォルダ選択、Manifestのファイル作成・保存、glTF読み込み、編集画面、トップ画面からのプレイは後続の実装対象。

### 段階2-Bの役割識別（2026-09-08、version 1）

- 親ノード方式をversion 1の規約として使用する。
- glTF 2.0の選択シーンを対象とする。default scene指定がなければ、シーンが1つのときだけ採用する。
- 大文字小文字を区別した `Visual` / `Hit` をMeshを持たない親ノードとして使用する。その子孫のMeshノードに役割を継承する。
- 両方の役割に少なくとも1つのMeshノードを要求する。役割ノードは複数でもよいが、入れ子は禁止。
- 役割の外にあるMesh、循環、同じノードの複数親、無効な参照、256段を超える階層はエラー。
- Meshノードは名前がなくてもよい。同じ名前や同じMesh参照でもノード番号で区別する。
- Inspect Rolesで、Visual/HitのMeshノード数・ノード番号・Mesh番号・名前を表示する。検査だけではManifestを変更しない。
- この検査はJSON階層のみを対象とし、頂点・インデックス・外部バッファ・画像・座標変換の妥当性を保証しない。
- GLBのヘッダーとチャンク境界を検査し、JSONチャンクのみ読み込む。JSONは16 MiBまで。BINを含む形状データは後続の読み込みで処理する。
